# Contributing

Thanks for helping improve Markdown Editor. This is a client-side app; keep changes focused and easy to review.

## Before you start

- Open an [issue](https://github.com/humaknlght/markdownweb/issues) for bugs or features when the change is non-trivial.
- **Security:** do not file a public issue. Use [private vulnerability reporting](https://github.com/humaknlght/markdownweb/security/advisories/new). See [SECURITY.md](SECURITY.md).

## Develop

```bash
npm install
npm run dev
```

Open [https://127.0.0.1:3456](https://127.0.0.1:3456) (self-signed TLS; accept the browser warning once). Edit under `src/`. More detail is in the [README](README.md).

## Tests

CI runs the full suite on every pull request. Locally:

```bash
npm test                 # unit + script checks
npx playwright install chromium   # once, for e2e
npm run test:e2e
npm run test:build       # production build invariants (slower)
npm run test:all         # everything CI runs
```

Prefer a failing test (unit or Playwright) when fixing a bug.

## Commit messages

Use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). A `commit-msg` hook (via Husky + commitlint) rejects non-conforming local commits; CI also checks the PR commit range.

Examples: `feat: add export`, `fix(drive): handle token refresh`, `docs: update CONTRIBUTING`.

## Pull requests

1. Branch from `main`.
2. Keep the diff scoped to one concern.
3. Ensure `npm run test:all` passes.
4. If you bump a CDN dependency (marked, DOMPurify, highlight.js, gemoji, yaml, Mermaid), run `npm run update:cdn-sri` and commit the updated `src/cdn-integrity.json`.
5. Open a PR against `main`. The **commitlint** and **test** status checks must pass before merge.

## Code notes

- Prefer small, readable changes that match existing style in `src/` (see folder layout in the README) and `test/`.
- Markdown is sanitized with DOMPurify; treat share links, uploads, and opened files as untrusted until Accept.
- Do not commit secrets, personal drafts, or `dist/` build output.
- `src/sw.js` is generated by `npm run dev` (not tracked). Production `sw.js` lives only under `dist/` after `npm run build`.

## Google Drive (optional)

Drive is **off** until the host provides credentials. Each deployment needs its **own** Google Cloud project (OAuth Client IDs are bound to that host’s origins). End users never type keys.

1. In [Google Cloud Console](https://console.cloud.google.com/), create (or pick) a project.
2. Enable **Google Drive API**.
3. Create an **OAuth 2.0 Client ID** (application type: Web application).
   - Authorized JavaScript origins: your prod origin and, for local work, `https://127.0.0.1:3456`.
   - Authorized redirect URIs (exact match required, including the trailing slash), for example:
     - `https://dev.ericperret.org/markdown/drive-helper/`
     - `https://127.0.0.1:3456/drive-helper/`
4. Copy the example and set `clientId` (this file is gitignored):

```bash
cp src/google-drive-config.example.json src/google-drive-config.json
# edit clientId
```

5. Dev: `npm run dev` serves `src/`, so the JSON is picked up immediately.  
   Production: `npm run build` copies `src/google-drive-config.json` into `dist/` when present. You can also place `google-drive-config.json` next to `index.html` on the server after deploy (no rebuild required).

| Key | Meaning |
| --- | --- |
| `clientId` | OAuth 2.0 Web client ID (required) |

If the file is missing or `clientId` is empty, Drive buttons stay hidden. Do not commit `google-drive-config.json`.

Sign-in runs in `drive-helper/` via an **OAuth 2.0 implicit grant** (`response_type=token`: Google returns a short-lived access token in the URL fragment; no `gsi/client` script, no client secret, and **no host-side token-exchange proxy** so the static server never sees the token). After Connect, the access token is kept **in memory only** (not written to `sessionStorage`, so XSS cannot scrape a stored copy). When WebAuthn **PRF** is available, the token is also **sealed** with AES-GCM into `localStorage` (ciphertext only); refresh / cold start / new tab uses **Unlock Drive** + passkey. Without PRF, refresh or closing the tab requires **Connect** again. Legacy IndexedDB silent vaults and any leftover plaintext session key are purged. **Disconnect** clears memory + sealed storage. Own `.htaccess` / SW bypass keep headers sane; `Permissions-Policy` allows `publickey-credentials-create|get` for `self`. The files drawer lists, opens, and saves under the **/markdown-editor** folder (including subfolders) via Drive REST on the main page. Scope: `drive.file`. The Drive folder name on Google’s side remains `markdown-editor`.

For OAuth branding / verification, the hosted privacy policy is `privacy.html` (for example `https://dev.ericperret.org/markdown/privacy.html`).

## GitHub Gist (optional)

Gist is **off** until the host enables it. End users paste their own fine-grained personal access token (the host never sees it). Browser OAuth is not used: GitHub’s token endpoint does not support CORS for static hosts without a server-side exchange.

1. Copy the example (this file is gitignored):

```bash
cp src/github-gist-config.example.json src/github-gist-config.json
# ensure "enabled": true
```

2. Dev: `npm run dev` serves `src/`, so the JSON is picked up immediately.  
   Production: `npm run build` copies `src/github-gist-config.json` into `dist/` when present. You can also place `github-gist-config.json` next to `index.html` on the server after deploy.

| Key | Meaning |
| --- | --- |
| `enabled` | When `true`, shows the Gist files-source and Connect UI |

If the file is missing or `enabled` is not true, Gist buttons stay hidden. Do not commit `github-gist-config.json`.

Users create a [fine-grained PAT](https://github.com/settings/personal-access-tokens) with **Gists** access, then **Connect Gist** and paste the token. The token is kept **in memory only**; when WebAuthn **PRF** is available it is also sealed like Drive. API calls use Octokit (bundled same-origin) to `https://api.github.com` only — not added to `img-src` / `script-src` / `frame-src`. Preview Markdown still cannot load remote images (`img-src` is `'self' data: blob:` only).
